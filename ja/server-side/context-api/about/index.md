</blockquote>


Context API は、現在の訪問コンテキストから対象を絞った一部のデータを迅速に取得する、構成可能なカスタマーデータプラットフォーム（CDP）API です。訪問プロファイル全体を返すのではなく、アプリ、サービスワークフロー、または AI システムが特定の判断やエクスペリエンスに必要とするオーディエンス、バッジ、属性のみを返します。Context API は、`utag.js` がインストールされている Tealium のクライアント側アプリケーション、Tealium for Mobile、または [マネージド MCP サーバー](#mcp-server)を介した LangChain などの任意のエージェント型 AI フレームワークに統合できます。

## 仕組み

Context API では、_エンジン_ と呼ばれる構成を使用して API レスポンスをカスタマイズし、現在の訪問について必要なデータのみを取得できます。たとえば、訪問プロファイル全体を取得する代わりに、エンジン構成で選択したオーディエンス、バッジ、属性データのみを取得します。

エンジンを構成すると、Context API によってワークフローに統合するための一意のエンドポイントが作成されます。

### ユースケース

Context API は、パーソナライズされたエクスペリエンスにリアルタイムの訪問データが必要となるあらゆる場面で使用できます。以下に例を示します。

* アクティブなセッションが確立される前の匿名訪問の検索を含む、最初のページ以降のパーソナライゼーション。
* データエンリッチメントロジックと組み合わせたネクストベストアクション。
* デバイスやチャネルを横断した訪問 ID 検索を使用するカスタマーサービスおよびクロスチャネルエクスペリエンス。
* マネージド MCP サーバーを介した AI およびエージェントベースのシステム。
* エンタープライズグレードの API 管理とコンプライアンス。

たとえば、訪問が Web サイトやアプリに戻ると、訪問データを取得するため、一意の Context API エンドポイントにリクエストが送信されます。Context API は必要なデータのみを提供するように最適化されているため、API はリアルタイムの効率的なレスポンスをアプリに返します。この重要なデータを使用して追加のロジックを有効化し、訪問にパーソナライズされたエクスペリエンスを提供できます。

### エンジン

Context API エンジンでは、一意の各エンドポイントに保存する訪問データと、それらのエンドポイントへのアクセスを許可するドメインを構成できます。

エンジンを構成する際は、ユースケースに必要なオーディエンス、バッジ、属性のみを選択します。Context API エンジンには、構築中の JSON レスポンスが表示されるため、リクエストの正確性と範囲を確認できます。

エンジンを有効にした後、訪問がアクティブなセッションを記録し、システム内でイベントを生成すると、その訪問のデータが利用可能になります。たとえば、訪問がサイトにアクセスすると、Context API は、新しい訪問イベントがエンジン構成で定義されているオーディエンス、バッジ、属性に影響するかどうかを判定します。訪問データの更新が必要な場合にのみ、各エンジン固有のデータストアにデータが書き込まれます。

エンジンはデータストアをリアルタイムで更新するため、訪問がブランドとやり取りする間も、API エンドポイントのデータは最新の状態に維持されます。

デフォルトでは、プロファイルごとに最大 10 個のエンジンを有効にできるため、特定のビジネスケースごとにカスタマイズしたエンジンを作成できます。追加のエンジンを有効にする必要がある場合は、Tealium サポートにお問い合わせください。

### 読み取りと書き込み

_読み取り_ とは、エンジンから訪問データを取得するリクエストです。データが見つかったかどうかにかかわらず、読み取りはクォータに対してカウントされます。レート制限によって Tealium が読み取りを拒否した場合、料金は発生しません。

_書き込み_ とは、Context API がエンジン用に保存している訪問プロファイルデータの更新です。統合された訪問については、Context API は、匿名 ID や構成済みの訪問 ID 値など、関連付けられた訪問 ID ごとに個別の書き込みを実行します。書き込みの合計数は、エンジン数と、統合された訪問にリンクされている関連訪問 ID の数によって異なります。

たとえば、ある訪問が 2 台のデバイスからサイトにアクセスした場合、2 つの匿名 ID が生成されます。

* デスクトップの匿名 ID `tealium_visitor_id` = `abc123`。
* モバイルの匿名 ID `tealium_visitor_id` = `bcd234`。

その結果、訪問プロファイル A と B が作成されます。

![](https://docs.tealium.com/images/server-side/visitor-stitching-example-first-visit.png)
![](https://docs.tealium.com/images/server-side/visitor-stitching-example-second-visit.png)  

訪問のメールアドレスは `user@example.com` です。この値が構成済みの訪問 ID 属性に入力され、両方のデバイスに関連付けられたプロファイルを新しいマスタープロファイル（C）に統合するために使用されます。

![](https://docs.tealium.com/images/server-side/visitor-stitching-profile-c-created.png)

アカウントにエンジンが 1 つあり、訪問が書き込み条件を満たす属性を持っている場合、システムは訪問プロファイルごとにそのデータを 1 回書き込みます。

* 訪問 ID 検索が有効な場合、3 回の書き込み（3 個の訪問プロファイル × 1 個のエンジン）。
* 訪問 ID 検索が無効な場合、2 回の書き込み（2 個の訪問プロファイル × 1 個のエンジン）。

![](https://docs.tealium.com/images/server-side/moments-api/moments-api-visitor-stitching-1.png)

アカウントに同一構成のエンジンが 5 つあり、訪問が書き込み条件を満たす属性を持っている場合、システムは訪問プロファイルごとにそのデータを 5 回書き込みます。

* 訪問 ID 検索が有効な場合、15 回の書き込み（3 個の訪問プロファイル × 5 個のエンジン）。
* 訪問 ID 検索が無効な場合、10 回の書き込み（2 個の訪問プロファイル × 5 個のエンジン）。

![](https://docs.tealium.com/images/server-side/moments-api/moments-api-visitor-stitching-2.png)

訪問の統合について詳しくは、[about-visitor-stitching](https://docs.tealium.com/about-visitor-stitching/)を参照してください。

### エンドポイント

Context API は、エンジンごとに一意のエンドポイントを作成します。訪問データは JSON オブジェクトとして返されます。

Tealium のベンチマークでは、ペイロードサイズが 1 kB 以下の場合、Context API エンドポイントの平均パフォーマンスは 60 ms です。

訪問データを取得するには、[タグ管理の高度な JavaScript コード拡張機能](https://docs.tealium.com/advanced-javascript-code-extension/)を構成し、[Context API エンドポイント](https://docs.tealium.com/context-api-endpoint/)にリクエストを送信します。


<blockquote>
エンジンを有効にしてからアクティブなセッションがない訪問については、データを利用できません。
</blockquote>


### MCP サーバー

Context API のマネージド MCP サーバーは、Model Context Protocol（MCP）を使用して、AI システムおよび LLM に訪問プロファイルデータへの安全なリアルタイムアクセスを提供します。Tealium がサーバーをホストおよび管理するため、デプロイまたは保守するインフラストラクチャはありません。AI エージェントはサーバーに接続し、パーソナライゼーション、分析、自動化に使用する対象を絞った顧客コンテキストを取得します。

このサーバーは匿名 ID と訪問 ID 属性の両方による検索をサポートしており、標準エンドポイントと同じ取得方法を使用できます。

詳しくは、[context-api-mcp-server](https://docs.tealium.com/context-api-mcp-server/)を参照してください。

### 訪問識別子

Context API エンドポイントは、Tealium の匿名 ID と訪問 ID 属性の両方を使用して訪問データを取得する GET リクエストをサポートしています。

* **匿名 ID**：サイトへのアクセス時またはアプリの使用時に、訪問に割り当てられる一意の匿名値です。匿名 ID を使用すると、同じブラウザーまたはアプリからの複数回のアクセスにわたって訪問を追跡できますが、異なるブラウザーやデバイスをまたいだ追跡はできません。
* **訪問 ID 属性**：ユーザー識別子から値を取得し、訪問の統合に使用される CDP の特殊な属性タイプです。

詳しくは、[匿名 ID、ユーザー識別子、訪問 ID 属性](https://docs.tealium.com/anonymous-user-visitor-id-attributes/)を参照してください。
### ガバナンス


<blockquote>
認証と PII の許可は、リクエストに応じてのみ利用できます。これらの機能を試すことに関心がある場合は、[サポートにお問い合わせください](https://docs.tealium.com/support/)。
</blockquote>


Context API には、安全な本番環境向けデプロイメントのための制御機能が組み込まれています。

* **認証**：各エンジンを **Public** または **Require Authentication** に構成します。認証が必要なエンジンは、Developer Portal で発行された有効なベアラートークンを含むリクエストのみを受け付けます。PII や制限付きデータを返すエンジンには、この構成を推奨します。詳細については、[dev-portal-subscriptions](https://docs.tealium.com/dev-portal-subscriptions/)を参照してください。
* **PII アクセス制御**：[制限付きデータ](https://docs.tealium.com/about-restricted-data/)としてマークされた属性は、デフォルトでは API レスポンスから除外されます。認証が必要なエンジンでは、エンジン構成で **Allow PII** を有効にすると、制限付き属性を含めることができます。
* **ドメイン許可リスト**：エンジンのエンドポイントを照会できるドメインを制限します。
* **フィルタールール**：エンジンへの書き込みとエンジンからの読み取りの対象となる訪問を制限します。詳細については、[フィルタールール](#filter-rule)を参照してください。
* **権限**：ロールベースのアクセス制御を使用して、エンジンを作成、編集、削除できるユーザーを制御します。
* **データのパージ**：訪問レコードに影響を与えることなく、古くなったエンジンデータへいつでもアクセスできないようにします。

詳細については、[ドメイン許可リスト](#domain-allowlist)、[権限](#permissions)、[データのパージ](#purge-data)を参照してください。

## 制限

Context API には、次のデフォルト制限があります。

* すべてのエンジンにわたるプロファイルごとの読み取りレート制限：200 リクエスト/秒/プロファイル
* プロファイルごとに有効化できるエンジンの最大数：10
* 訪問ごと、エンジンごとに保存できる Context API データの最大サイズ：1 kB 
<blockquote>
訪問属性データがデータストアの上限を超えた場合、その訪問のデータは保存されません。
</blockquote>

* Context API エンドポイントでデータを利用できる期間：新しいイベントが処理されない場合は 30 日間

ユースケースでより高い上限が必要な場合は、Tealium のアカウントマネージャーにお問い合わせください。

## データのパージ

Context API では、データのパージ機能を使用して、古くなったエンジンデータへアクセスできないようにできます。

次の例は、エンドポイントからデータをパージする必要がある状況を示しています。

* エンジン構成に含まれるオーディエンス、バッジ、または属性の名前を変更または削除する場合。
* 属性の個人識別情報（PII）ステータスを変更する場合。属性の PII ステータスを変更しても、機密情報が API エンドポイントに引き続き保存されている可能性があります。
* エンジン構成からオーディエンス、バッジ、または属性を削除する場合。
* エンジンで **Allow PII** を無効にする場合。制限付き属性は、それ以降のレスポンスから直ちに削除されますが、以前に保存されたデータはパージするまでエンジンに残ります。パージすると、そのデータへアクセスできなくなります。

エンジンで使用されているオーディエンス、バッジ、または属性が CDP またはエンジン構成から削除されると、その項目は以降エンドポイントに入力されなくなります。削除された属性を含むエンジンデータは変更されません。一般に、依存項目を削除することでエンドポイント統合に破壊的変更が生じる場合は、エンジンデータをパージすることを推奨します。


<blockquote>
データのパージは、Context API のエンジンデータにのみ影響します。訪問レコードには影響しません。
</blockquote>


エンジンデータのパージの詳細については、[Context API エンジンの管理 > データのパージ](https://docs.tealium.com/context-api-manage-engines/#purge-data)を参照してください。

## ドメイン許可リスト


<blockquote>
ドメイン許可リストは、API エンドポイントをテストした後に作成することを推奨します。
</blockquote>


許可リストを使用すると、信頼されていないドメインから Context API エンドポイントへのリクエストを防止できます。エンジンを構成するときに、特定のドメインを許可リストへ追加します。

Context API は、`Referer` HTTP リクエストヘッダー内のドメインを Context API エンジンに定義された許可リストと比較し、エンドポイントへの呼び出しを許可または制限します。

* ドメインが一致する場合：リクエストが処理されます。
* ドメインが一致しない場合：リクエストは処理されず、403 エラーが返されます。

ドメインを何も指定しない場合、すべてのドメインが許可されます。

### サブドメイン

ドメインを許可リストに追加すると、そのすべてのサブドメインが自動的に含まれます。たとえば、`example.com` を許可すると、`*.example.com` に一致するすべてのサブドメインが含まれます。

## 権限

Context API の機能は、次の権限レベルによって管理されます。

* **エンジンの作成、編集、削除、およびエンジンデータのパージ**
  * 従来の Editor または Publisher 権限
  * プラットフォーム権限の書き込みまたは削除アクセス
* **エンジンリストの表示**
  * 従来の Viewer 権限、またはプラットフォーム権限の読み取りアクセス

## フィルタールール

フィルタールールは、各エンジンの **Details** タブで構成するオプションの条件です。有効にすると、そのエンジンへの書き込みと、そのエンジンからの読み取りの対象となる訪問を制限します。

同意した訪問だけにアクセスできることを保証するための同意適用や、テスト用または限定的な範囲のエンジンで課金対象となる書き込み量を減らすためのコスト管理に、フィルタールールを使用します。

デフォルトでは、すべての訪問が書き込みおよび読み取りの対象になります。フィルタールールを追加すると、両方の動作が次のように変わります。

* **書き込み**：訪問属性がルールの条件に一致する訪問のみが、エンジンへの書き込みをトリガーします。
* **読み取り**：エンジンは、フィルターに一致する訪問のみを返します。一致しない訪問については、以前にその訪問の書き込みが行われていた場合でも 404 が返されます。

フィルタールールには訪問属性のみを使用できます。訪問およびイベント属性は条件として使用できず、**has changed** 演算子も使用できません。


<blockquote>
**Filter Rule** セクションは、プロファイルがバージョン管理された保存に移行された後にのみ表示されます。従来のエンジンがある場合は、フィルタールールを構成する前に[移行](https://docs.tealium.com/context-api-manage-engines/#migrate-engine-configuration)を完了してください。
</blockquote>


フィルタールールを追加または削除する手順については、[フィルタールールの追加](https://docs.tealium.com/context-api-manage-engines/#add-a-filter-rule)を参照してください。

## Context API と Data Layer Enrichment API の比較

Context API と [Data Layer Enrichment API](https://docs.tealium.com/data-layer-enrichment-public-api/)は、どちらもライブ訪問データを取得できますが、ユースケース、構成、および実装が異なります。これら 2 つの訪問プロファイルデータ取得方法の違いについては、次の比較を参照してください。

| | **Context API**| **Data Layer Enrichment API**|
|---|---|---|
|**ユースケース**|最初のページからそれ以降までのパーソナライゼーションに使用する、現在の訪問データへのリアルタイムアクセス。|最初のイベントが処理された後、リアルタイムから準リアルタイムで利用できるライブ訪問データ。|
|**レート**|200 リクエスト/秒|-|
|**アクティブな訪問セッションが必要**|いいえ|はい|
|**利用可能なデータ**|オーディエンス、バッジ、または[サポート対象の属性データ型](https://docs.tealium.com/context-api-endpoint/#objects)。<br>オーディエンスおよびバッジの名前と ID を利用できます。|訪問 ID、ファネル、タイムライン以外の属性が、属性 ID 別に一覧表示されます。バッジとオーディエンスについては、名前を利用できます。<br>バッジ名については、[Profile Definition API](https://docs.tealium.com/get-profile-definition-api/)と組み合わせて使用します。|
|**検索 ID**|Tealium 匿名 ID または訪問 ID 属性値|Tealium 匿名 ID|
|**認証済みエンドポイント**|オプション。エンジンでは、Developer Portal を介した認証を必須にできます。|いいえ|
|**PII へのアクセス**|オプション。認証が必要なエンジンで **Allow PII** を有効にすると、制限付き属性を含めることができます。|いいえ|
|**カスタムレスポンスオブジェクト**|はい|いいえ|
|**実装**|API|API または Tealium Collect タグ|

## はじめに

Context API を使用するワークフローには、次の手順が含まれます。

1. パーソナライズされたエクスペリエンスを作成するために必要なオーディエンス、バッジ、属性を検討します。
1. 必要な訪問データをカスタマイズ済みエンドポイントに格納するため、Context API エンジンを作成します。
1. utag.js がインストールされている Tealium クライアント側アプリケーション、または Tealium for Mobile にエンドポイントを統合します。
1. データを収集してアクティブ化します。
