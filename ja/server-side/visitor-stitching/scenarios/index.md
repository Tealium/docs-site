同じユーザーが2つのメールアドレスで識別された場合、その結果は、それぞれで使用されたデバイスとブラウザに基づきます。

たとえば、ユーザーが初めてWebサイトにアクセスし、フォームを送信する際にメールアドレスを入力したとします。メールアドレスはハッシュ化され、`Email Address Hash`訪問ID属性がエンリッチされ、Customer Data Platform（CDP）に新しい訪問プロファイルが作成されます。

作成された訪問プロファイルは、次のようになります。

|属性|値|
|---|---|
|匿名ID|01754649ad73005a6d584d2732c401078005b0700093c|
|デバイス|ノートパソコン|
|ブラウザ|Chrome 89|
|メールアドレスのハッシュ|16c18d336f0b250f0e2d907452ceb9658a74ecdae8bc94864c23122a72cc27a5|

## シナリオ1：同じデバイスとブラウザから別のメールアドレスを使用する

1週間後、ユーザーが同じデバイスとブラウザを使用してWebサイトにアクセスし、別のメールアドレスでフォームを送信します。これには、次の2つのケースがあります。

* ケースA：同じユーザーがアクセスし、別のメールアドレスでフォームを送信する。
* ケースB：2人のユーザーが1台のデバイスを共有し、別のユーザーが別のメールアドレスでフォームを送信する。

### ケースA

匿名IDが同じであるため、受信イベントはユーザーの初回訪問時に作成されたプロファイルと一致します。ただし、訪問ID属性は変更できないため、新しいメールアドレスのハッシュ値は使用されません。

**ケースAの結果：** 訪問ID属性に元のメールアドレスのハッシュが構成された、1つの訪問プロファイル。

![](https://docs.tealium.com/images/server-side/two-emails-first.png)

### ケースB

デバイスを共有するユーザーが、異なるユーザー識別子（この場合はメールアドレス）を使用して同じWebサイトにアクセスすることを、訪問の切り替えと呼びます。訪問の切り替えに対応するソリューションの実装については、Tealiumサポートまたはプロフェッショナルサービスが支援します。詳細については、次のTealiumナレッジベースの記事を参照してください。

* [CDPでの訪問切り替えを使用した、ITP環境下での匿名ユーザーのトラッキング](https://support.tealiumiq.com/en/support/solutions/articles/36000441645-anonymous-user-tracking-under-itp-with-visitor-switching-in-audiencestream)
* [iQでの訪問の切り替え](https://support.tealiumiq.com/en/support/solutions/articles/36000419055-visitor-switching-in-iq)
* [Tealium Mobile SDKでの訪問の切り替え](https://support.tealiumiq.com/en/support/solutions/articles/36000493080-visitor-switching-in-tealium-mobile-sdks)

## シナリオ2：別のデバイスまたはブラウザから別のメールアドレスを使用する

1週間後、同じユーザーが別のデバイスまたはブラウザを使用してWebサイトにアクセスし、別のメールアドレスでフォームを送信します。匿名IDが異なるため、受信イベントはユーザーの初回訪問時に作成されたプロファイルと一致しません。新しいプロファイルが作成され、2回目の訪問後には、このユーザーに対して2つのプロファイルが存在することになります。訪問ID属性が一致しない（メールアドレスが異なる）ため、訪問スティッチングは行われません。これら2つのプロファイルは、後で2番目の訪問ID属性が一致した場合にスティッチングできます。

**結果：** 2つの訪問プロファイルが作成され、それぞれの訪問ID属性に対応するメールアドレスのハッシュが構成されます。

![](https://docs.tealium.com/images/server-side/two-emails-both.png)

## 2番目の訪問ID属性が一致する2つの訪問プロファイルの例

この例では、ユーザーが2台の異なるデバイスからWebサイトにアクセスし、訪問ごとに顧客IDが割り当てられます。匿名IDが一致しないため、2つの異なるプロファイルが作成されます。顧客IDは訪問ID属性#1をエンリッチするように構成されており、次に示すように、各プロファイルの訪問ID属性がエンリッチされます。

このシナリオが発生する可能性があるのは、匿名ID（`tealium_visitor_id`）が不明であるか、2つのプロファイルで異なる場合のみです。匿名IDが一致する場合、ユーザーIDや訪問ID属性は評価されず、2番目のプロファイルは作成されません。

![](https://docs.tealium.com/images/server-side/match-2nd-visid-first.png)

ユーザーが最初のデバイスから再度Webサイトにアクセスし、フォームを送信する際にメールアドレスを入力します。customer_emailアドレス属性は、訪問ID属性#2をエンリッチするように構成されています。次に示すように、プロファイルAの訪問ID属性#2がメールアドレスでエンリッチされます。

![](https://docs.tealium.com/images/server-side/match-2nd-visid-second.png)

ユーザーが2番目のデバイスからWebサイトにアクセスし、フォームを送信する際に同じメールアドレスを入力すると、そのメールアドレスがプロファイルAの訪問ID属性#2と一致します。次に示すように、2つのプロファイルがスティッチングされ、プロファイルCが作成されます。

![](https://docs.tealium.com/images/server-side/match-2nd-visid-third.png)

プロファイルCには新しい`replaces`配列が含まれます。この配列には、訪問ID属性には保存されなくなったものの、今後も訪問スティッチングに使用できる値が保持されます。プロファイルAとプロファイルBでは、匿名IDと訪問ID属性#1（顧客ID）の値が異なっていました。訪問ID属性ごとに構成できる値は1つだけであるため、2つの値を`replaces`配列に移動する必要がありました。プロファイルBはプロファイルAより新しく、イベント数も少なかったため、プロファイルBの識別子が`replaces`配列に移動されました。

### HTTP APIとファイルインポートのデータソース

WebまたはHTTP APIのデータソースでは、このシナリオが発生するのは、訪問ID属性#1（顧客ID）の属性ID値が訪問ID属性#2（ハッシュ化されたメールアドレス）より小さい場合のみです。

ファイルインポートでは、訪問IDのマッピングをカスタマイズでき、ユーザー識別子のエンリッチメントはマッピングされた順序で行われます。そのため、構成に応じて、いくつかの異なる方法でこのシナリオを実現できます。

詳細については、[Tealium Collect HTTP API](https://docs.tealium.com/platforms/http-api//)、[受信Webhookについて]()、または[ファイルインポートについて]()を参照してください。

#### ステートレスイベント

HTTP APIとファイルインポートはどちらも、`tealium_visitor_id`の値が自動的に割り当てられないため、ステートレスイベントを送信します。HTTP APIリクエストでは、`tealium_visitor_id`が構成されていない限り、各イベントによって新しい訪問プロファイルが生成されます。このような場合、`tealium_visitor_id`に独自の匿名値を生成することをお勧めします。

通常、ファイルインポートのデータソースには、訪問ID属性にマッピングされるユーザー識別子が含まれています。

HTTP APIリクエストまたはファイルインポートのマッピングに`tealium_visitor_id`の値が含まれていない場合、CDPは匿名IDにランダムな値を割り当て、訪問スティッチングの前に新しい訪問プロファイルを作成します。

## その他のシナリオ

### スティッチイベントの際に2つの異なる訪問ID属性値が存在する場合はどうなりますか？

2つの訪問ID属性が定義されています。1つの訪問ID属性はメールアドレスを取得し、もう1つはXのハンドル名を取得します。

ユーザーがコンピューターからサイトにアクセスし、`marketer@xyzcorp.com`というメールアドレスを使用してニュースレターに登録します。同じセッション内で、ユーザーは製品を見つけ、`marketerxyz`というXのハンドル名を使用してその製品について投稿します。その後、ユーザーはタブレットを使用し、`name@xyzcorp.com`というメールアドレスで注文を送信します。続いて、`marketerxyz`というXのハンドル名を使用して、その注文について投稿します。

Xのハンドル名が一致したため、訪問スティッチングの一致が発生します。Xのハンドル名は同じですが、メールアドレスは異なります。この場合、どうなるでしょうか？
#### 回答
2つのデバイスのプロファイルは、Xハンドルに基づいてスティッチされます。

プライマリのスティッチ済みプロファイルが作成されると、Xハンドル用とメールアドレス用の2つのセカンダリIDが作成されます。両方のデバイスでハンドルが同じであるため、XハンドルのセカンダリIDは `marketerxyz` に構成されます。

訪問のスティッチ時には、各プロファイルの過去のイベントがすべて時系列順に並べられ、再処理されます。メールのセカンダリIDには、再処理中に最初に検出されたメールアドレスが構成されます。この場合は `marketer@xyzcorp.com` です。

以降は、どちらのメールアドレスを使用しても、その訪問プロファイルにスティッチできます。これは、異なるメールアドレスとプロファイルを持つ2台の別々のデバイスがあり、後からXハンドルに基づいてスティッチされたためにのみ適用されます。

### 属性値が異なる2つの訪問プロファイルをスティッチするとどうなりますか？

2つの訪問プロファイルをスティッチする際、それぞれのプロファイルに同じ属性が異なる値で存在する場合、どうなるのでしょうか？

例：

* デスクトップデバイスでは、「オプトインステータス」フラグが「True」
* モバイルデバイスでは、「オプトインステータス」フラグが「False」

#### 回答

最初に、システムの重要な機能をいくつか理解しておく必要があります。

* イベントがCDPに送られると、それらのイベントを使用して訪問プロファイルが作成されます。
* 訪問の訪問が期限切れになると、訪問とその訪問に含まれるすべてのイベントが、2つの異なるDBコレクション（EventStoreログとは別）に保存されます。
* 訪問のライフタイム全体では、数百件、場合によっては数千件のイベントが発生することがあります。ほとんどの場合、これらの永続化されたイベントは使用されることなく、訪問プロファイルの期限切れとともに期限切れになります。

この前提を踏まえて、スティッチイベントの発生時に何が起こるかを説明します。一致するプロファイルが見つかると、CDPはスティッチ対象となるすべての訪問について過去のイベントをすべて読み込み、各イベントを時系列順に並べて再生し、プライマリのスティッチ済みプロファイルを作成します。

元の質問に戻ると、`Opt-In Status` フラグが `True` と `False` のどちらに構成されるかは、CDPがこれらの訪問の過去のイベントをすべて再生する際に再処理される、すべてのエンリッチメントの結果によって決まります。

#### 補足事項と想定される質問

`list` や `tally` など、より高度な属性について疑問を持つかもしれません。`tally` 属性と `list` 属性はマージされているように見えますが、これは加算型のエンリッチメント（リストへの追加、集計値の増加など）を使用して構成されているためです。通常、これらは以前から正しくスティッチされています。

イベント数によっては、スティッチは非常に複雑でCPU負荷の高い処理であるため、実行に時間がかかる場合があります。しかし、過去数年間にわたり、エンジニアリングチームはこのスティッチ処理を効率化するために数多くの最適化を行ってきました。通常は非常に短時間で完了します。

これは、スティッチに後方互換性があるということでしょうか？次のようなイベントのシナリオを考えてみましょう。

* 顧客がデスクトップからWebサイトに登録する

  * customer_typeがASに渡される
  * customer_emailがASに渡される

* CDP内

  * customer_emailを使用して訪問IDが割り当てられる
  * customer_typeは無視される

* 1週間後、`customer_type` を保存するTraitが作成される
* 2週間後、訪問が同じ `customer_email` 値を使用してモバイルで認証する（ただし、`customer_type` は渡されない）
* デスクトップとモバイルのプロファイルをスティッチする

`customer_type` を取得するTraitは、どちらのデバイスの訪問プロファイルにも存在していません。しかし、ASがすべてのイベントを再処理すると、CDPは最新のCDPプロファイル定義を使用してTraitのエンリッチメントを再評価します。つまり、プライマリ訪問プロファイルには、`customer_type` を保存するTraitが含まれるようになります。

#### これはオムニチャネルデータにどのような影響を与えますか？

オムニチャネルデータはイベントデータとして扱われ、同じように動作します。つまり、イベントデータはイベントデータベースに保持され、オンラインイベントデータの一部として時系列順に扱われます。

#### これはAudienceStoreのタイムラインのタイムスタンプと、オーディエンスへの参加日／離脱日にどのような影響を与えますか？

タイムスタンプはスティッチイベントが発生した時点ではなく、個々のイベントが発生した時点を表します。
