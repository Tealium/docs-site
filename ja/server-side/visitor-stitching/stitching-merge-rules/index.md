## 要件

* Customer Data Platform（CDP）が有効であること
* 訪問スティッチングが有効であること
* アカウント管理者権限

## スティッチングマージルールの仕組み

訪問スティッチングでは、イベントリプレイを使用して過去のイベントからマージ済みプロファイルを構築しますが、イベントの保持期間や最大 1,500 件というイベント数など、システム上の制限があります。訪問プロファイルがこれらの制限を超えると、スティッチング中に古いイベントがリプレイされず、長期間存続しているプロファイルやイベント量の多いプロファイルでは、履歴データが不完全になる場合があります。

スティッチングマージルールは、イベントリプレイに依存しない属性固有のロジックをスティッチングプロセスに追加し、毎回同じ永続的かつ一貫した結果を生成することで、このような問題に対処します。

マージルールでは、2 つの訪問プロファイルの属性を比較して最終的な属性値を決定します。この値は、マージ済み訪問プロファイルで過去のイベントがリプレイされた後に適用されます。これにより、過去のすべてのイベントを処理できない場合でも、最も重要な属性に意図した値を保持できます。

### マージルールが適用される場合

スティッチングマージルールは、過去にアクティビティがある 2 人の訪問をスティッチングする場合にのみ適用されます。このシナリオでは、イベントリプレイによって古いイベントが破棄される可能性があるため、最終的な属性値を決定するルールが必要です。

マージ対象のいずれかの訪問に過去の訪問がない場合、再訪問のイベントリプレイによって結果が決まるため、スティッチングマージルールは適用されません。

## マージルールが必要な属性の特定

すべての属性にスティッチングマージルールが必要なわけではありません。そのため、まず、どの重要な属性がスティッチングマージルールから最も大きなメリットを得られるかを判断します。一般的に、スティッチングマージルールは、生涯値を追跡する最も重要な属性と、データプライバシーおよび同意に関連する属性にのみ使用します。

次のカテゴリの属性は、スティッチングマージルールに適しています。

* **同意ステータス属性**  
同意を決定したイベントが保持期間よりも古い場合や、イベント量によって対象外になった場合でも、正しい同意ステータスを維持します。    
* **ライフタイム指標**  
カウンター、集計値、累積値の正確性を維持します。    
* **CRM／ファイルからインポートされた属性**  
記録システム（CRM など）からインポートされた信頼できる値を維持します。

### エンリッチメントの分析

スティッチングマージルールが必要な属性を特定したら、次に、そのエンリッチメントのロジックに基づいて最適なルールを選択します。

適切なマージルールを選択するには、エンリッチメントによって属性がどのように構成されるかを理解する必要があります。スティッチング後の結果がエンリッチメントの意図と一致するよう、同じ判定ロジックを適用するマージルールを選択してください。意図されたエンリッチメントのロジックと異なるルールを使用すると、データに不整合が生じる可能性があります。

特定のエンリッチメントに最適なスティッチングマージルールの例については、[定義](#definitions)を参照してください。

## 属性固有のマージ動作

### プリロード済み属性

プリロード済み属性は、Customer Data Platform（CDP）が有効になっているすべてのプロファイルに存在する、システム管理の属性です。スティッチングマージルールを有効にすると、これらの属性には、リプレイ結果と整合する適切なマージルールが自動的に適用され、その選択を編集することはできません。これにより、組み込みのエンリッチメントとの整合性が維持されます。

詳細については、[preloaded-attributes](https://docs.tealium.com/preloaded-attributes/)を参照してください。

### ファネル

ファネル属性タイプでサポートされるスティッチングマージルールは、**ファネルをマージ**のみです。

**ファネルをマージ**ルールは、各訪問のファネルステップを時系列順に結合します。重複するステップが存在する場合は、先に発生したステップが保存され、古い方が削除されます。

### 集計のお気に入り

集計のお気に入りでは、**再計算（強制）**ルールのみを使用できます。集計属性は、最も大きい値を持つ集計キーを格納するお気に入り属性を生成するため、マージ済み訪問で常に再計算する必要があります。

集計属性とそれに関連付けられたお気に入り属性は、次のように動作します。

* 集計にマージルールがある場合、お気に入り属性には**再計算（強制）**ルールが自動的に適用されます。これにより、他のマージルールの実行後、スティッチング済み訪問でその値が再計算されます。
* 集計にマージルールがない場合、お気に入り文字列にもマージルールは自動的に構成されません。
* 集計からマージルールを削除すると、お気に入り属性のマージルールも自動的に削除されます。

### タイムライン

タイムライン属性タイプでサポートされるスティッチングマージルールは、**タイムラインをマージ**のみです。

**タイムラインをマージ**ルールは、各訪問のエントリを時系列順に結合し、上限を超えた場合は、最新の 100 件のエントリだけが残るように結果を切り詰めます。

タイムライン属性に、`X` 日より古いエントリを期限切れにするエンリッチメントがある場合、マージルールはマージ時点から `X` 日より古いエントリを期限切れにします。複数のエンリッチメントがエントリを期限切れにする場合、マージルールでは最も小さい `X` の値が使用されます。

### 訪問 ID

スティッチングマージルールを有効にすると、各訪問 ID 属性に**古い方**ルールが自動的に適用されます。訪問 ID 属性の**古い方**ルールは変更できません。

## スティッチングマージルールの使用

スティッチングマージルールを使用するには、まずこの機能を有効にする必要があります。

プロファイルでスティッチングマージルールを有効にするには、次の手順を実行します。

1. **管理 > サーバーサイド構成**に移動します。
1. **スティッチングマージルール**トグルをクリックしてオンにします。
1. **保存**をクリックします。
1. プロファイルをパブリッシュします。

スティッチングマージルールを有効にすると、属性編集ビューで新しい構成を利用できるようになります。属性にマージルールを適用するには、この構成を有効にしてから、リストからマージルールを選択します。

## 定義

### And

| サポートされるデータ型 | ルールの動作 |
|----------------------|---------------|
|  バッジ | 両方が `Assigned` の場合にのみ `Assigned` に構成します。 |
|  ブール値 | 両方が `true` の場合にのみ `true` に構成します。 |
{class="dt--fixed"}

**例**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-and-example.png)

この例の属性は、訪問のすべてのオンライン訪問が PPC 経由であった場合に、その訪問について `true` になります。これらのエンリッチメントに基づき、両方の訪問の属性が `true` に構成されている場合にのみ、統合後の属性が `true` になります。いずれかの訪問の属性が `false` に構成されている場合、その訪問のオンライン訪問のすべてが PPC 経由ではなかったことを意味するため、統合後の属性値は `false` になります。正しい統合値を得るには、**And** ルールを使用します。

**バッジ**：
| 訪問 A | 訪問 B | **And** ルールで統合された訪問 |
| ----- | -----  | ----- |
| `Assigned` | `Assigned`  | `Assigned` |
| `Assigned` | `Not Assigned`  | `Not Assigned` |
| `Not Assigned` | `Assigned`  | `Not Assigned` |
| `Not Assigned` | `Not Assigned`  | `Not Assigned` |

**ブール値**：
| 訪問 A | 訪問 B | **And** ルールで統合された訪問 |
| ----- | -----  | ----- |
| `True` | `True`  | `True` |
| `True` | `False`  | `False` |
| `True` | （未構成）  | `False` |
| `False` | `True`  | `False` |
| `False` | `False`  | `False` |
| （未構成） | `True`  | `False` |
| （未構成） | （未構成）  | （未構成） |

### Or

| サポートされるデータ型 | ルールの動作 |
|----------------------|---------------|
|  バッジ | いずれかが `Assigned` の場合、`Assigned` に構成します。 |
|  ブール値 | いずれかが `true` の場合、`true` に構成します。 |
{class="dt--fixed"}

**例**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-or-example.png)

この例のバッジは、訪問が一度限りのイベントを確認すると割り当てられ、その後割り当てが解除されることはありません。

これらのエンリッチメントに基づき、いずれかの訪問が登録済みであれば、統合後のバッジが割り当てられます。そのため、正しい結果を判定するには **Or** ルールが適切です。

**バッジ**：
| 訪問 A | 訪問 B | **Or** ルールで統合された訪問 |
| ----- | -----  | ----- |
| `Assigned` | `Assigned`  | `Assigned` |
| `Assigned` | `Not Assigned`  | `Assigned` |
| `Not Assigned` | `Assigned`  | `Assigned` |
| `Not Assigned` | `Not Assigned`  | `Not Assigned` | 

**ブール値**：
| 訪問 A | 訪問 B | **Or** ルールで統合された訪問 |
| ----- | ----- | -----  |
| `True` | `True` | `True`  |
| `True` | `False` | `True`  |
| `True` | （未構成） | `True`  |
| `False` | `True` | `True`  |
| `False` | `False` | `False`  |
| （未構成） | `True` | `True`  |
| （未構成） | （未構成） | （未構成）  |

### より新しい

**より新しい**ルールでは、削除された値を含め、最も新しく更新された属性値が選択されます。このルールは、（他の訪問属性ではなく）受信イベントの属性に基づくエンリッチメントを持つ属性に最適です。

**より新しい**ルールは、エンリッチメントによって属性値が更新されたときに構成される内部タイムスタンプに基づきます。両方の属性に内部タイムスタンプが構成されていない場合は、各訪問の最終訪問のタイムスタンプを使用して、どちらが先に構成されたかを判定します。

| サポートされるデータ型 | ルールの動作 |
|-------------|--------------------|
|  バッジ | より新しく更新された状態（未割り当てを含む）を保持します。 |
|  ブール値<br>  数値 | より新しく更新された値を保持します。 |
|  日付 | より新しく更新された値（削除された値を含む）を保持します。これは、属性自体に保存されている日付値ではなく、この日付属性が最後にエンリッチされた日時に基づきます。 |
|  文字列セット | より新しく更新された文字列セット（削除されたセットを含む）を保持します。 |
|  文字列 | より新しく更新された値（削除された値を含む）を保持します。 |
|  集計 | より新しく更新された集計（削除された集計を含む）を保持します。 |
|  ブール値の配列<br>  数値の配列<br>  文字列の配列 | より新しく更新された配列（削除された配列を含む）を保持します。 |
{class="dt--fixed"}

### より古い

**より古い**ルールでは、削除された値を含め、より前に更新された属性値が選択されます。**より古い**ルールは、値がまだ構成されていない場合にのみ値を構成するエンリッチメントを持つ属性に最適です。これにより、その訪問について最初の値のみが保存されます。

**より古い**ルールは、エンリッチメントによって属性値が更新されたときに構成される内部タイムスタンプに基づきます。両方の属性に内部タイムスタンプが構成されていない場合は、各訪問の最終訪問のタイムスタンプを使用して、どちらが先に構成されたかを判定します。


<blockquote>
属性のエンリッチメントで自己参照ルールを使用して一度だけ構成されるようにしていない場合、**より古い**ルールを使用しても、必ずしも最初に構成された値が得られるとは限りません。
</blockquote>

### 再計算

| サポートされるデータ型 | ルールの動作 |
|----------------------|---------------|
|  バッジ | 以前の状態を破棄し、最終的にマージされたプロファイルに対してエンリッチメントを実行します。 |
|  ブール値<br> 日付<br> 数値 | 以前の値を破棄し、最終的にマージされたプロファイルに対してエンリッチメントを実行します。 |
|  文字列セット<br> 文字列<br> 集計<br> ブール値の配列<br> 数値の配列<br> 文字列の配列 | 未割り当ての状態から開始し、最終的にマージされたプロファイルに対してエンリッチメントを実行します。 |
{class="dt--fixed"}

**再計算**ルールでは、属性の初期マージ値を破棄し、その属性のエンリッチメントを再実行します。初期マージ値を破棄することで、未構成の値から再計算が開始され、エンリッチメントのみに基づいて値が構成されます。

**再計算**ルールは、文字列セット内の項目をカウントする数値属性など、他の訪問属性または訪問属性から派生する属性に最適です。このような場合、まずソース属性が、構成されていれば他のマージルールを使用して解決され、その後、**再計算**ルールによって派生値が再計算されます。

**ルールの動作**：

* エンリッチメントが**新規訪問**、**新規訪問**、または**訪問終了**時に実行されるよう構成されている場合、マージの原因となったイベントによって**新規訪問**、**新規訪問**、または**訪問終了**も発生した場合にのみ、マージルール内で実行されます。
* イベント属性を使用するエンリッチメントルールの条件は、マージの原因となったイベントに基づいて評価されます。
* **変更あり**演算子を使用するエンリッチメントルールの条件は、確認対象の属性値がいずれかのプロファイルと異なる場合、`true`と評価されます。

**例**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-recalculate-example.png)

この例では、属性値は別の訪問属性である`Orders Timeline`から派生しています。`Orders Timeline`属性に独自のマージルール（**タイムラインをマージ**）がある場合、**再計算**ルールによってこの数値属性が評価される前に、そのルールが実行されます。
### 再計算（強制）

**再計算（強制）**ルールは**再計算**ルールと同じですが、複数のエンリッチメント条件を強制的に `true` に構成する点が異なります。**再計算（強制）**ルールは、1 つ以上の他の訪問属性または訪問属性の値から派生する属性で、それらの属性も**新規訪問**、**新規訪問**、または**訪問終了**のいずれかの条件を使用している場合に最適です。

訪問のスティッチングは、**新規訪問**、**新規訪問**、または**訪問終了**の条件と一致しないタイミングで発生することがあります。そのため、このルールでは、正しい値が構成されるように、それらのエンリッチメントを強制的に実行します。

**ルールの動作**：

* エンリッチメントが**新規訪問**、**新規訪問**、または**訪問終了**で実行されるように構成されている場合、マージの原因となったイベントによって**新規訪問**、**新規訪問**、または**訪問終了**が発生していなくても、マージルール内で強制的に実行されます。
* イベント属性を使用するエンリッチメントルールの条件は、強制的に `true` と評価されます。
* **変更あり**演算子を使用するエンリッチメントルールの条件は、強制的に `true` と評価されます。

| サポートされるデータ型 | ルールの動作 |
|----------------------|---------------|
|  バッジ | 以前の状態を破棄し、最終的にマージされたプロファイルでエンリッチメントを実行して、一部の条件を強制的に `true` にします。 |
|  ブール値<br> 日付<br> 数値 | 以前の値を破棄し、最終的にマージされたプロファイルでエンリッチメントを実行して、一部の条件を強制的に `true` にします。 |
|  文字列セット<br> 文字列<br> 集計<br> ブール値の配列<br> 数値の配列<br> 文字列の配列 | 未割り当ての状態から開始し、最終的にマージされたプロファイルでエンリッチメントを実行して、一部の条件を強制的に `true` にします。 |
{class="dt--fixed"}

**例**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-recalculate-force-end-visit.png)

この例では、この属性は別の訪問属性 `Lifetime visit count` から派生し、訪問の訪問回数が 10 回以上になるとバッジを割り当てます。ただし、エンリッチメントは `Visit Ended` で実行されるように構成されており、訪問のスティッチングが発生した時点ではこの条件が成立していない可能性があります。そのため、**再計算（強制）**ルールを使用すると、エンリッチメントが強制的に実行されます。

`Visit Ended` が強制的に `true` と評価されない場合、バッジは訪問が終了するまで未割り当てのままとなり、訪問がこのバッジに基づくオーディエンスから離脱した後、再び参加する可能性があります。オーディエンスからの離脱やオーディエンスへの参加によってコネクタアクションが実行される場合、この動作は望ましくない可能性があります。

### 合計

**合計**ルールは、各数値属性の値の合計を保持します。一方の値が構成されていない場合、構成されているもう一方の値が結果になります。どちらの値も構成されていない場合、マージ後の値も構成されません（値 `0` にはなりません）。

| サポートされるデータ型 | ルールの動作 |
|----------------------|---------------|
|  数値 | 両方の訪問の値を加算します。 |
{class="dt--fixed"}

![](https://docs.tealium.com/images/server-side/merge-rules/rule-sum-example.png)

この例では、訪問 A が 30 ドル、訪問 B が 60 ドルを支出していた場合、マージ後の訪問の支出額は 90 ドルになります。

### 和集合

**和集合**ルールは、両方の属性の値を結合し、配列間で一貫した順序を維持します。文字列セット内の値は重複が削除されます。

| サポートされるデータ型 | ルールの動作 |
|----------------------|---------------|
|  文字列セット | 両方の値を結合します。 |
|  ブール値の配列<br> 数値の配列<br> 文字列の配列 | 両方の値を結合し、配列間で一貫した順序を維持します。 |
{class="dt--fixed"}

**例：文字列セット**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-union-set-example.png)

この例では、**和集合**ルールによってエントリが結合されます。また、文字列セット内のエントリは一意である必要があるため、水曜日の重複エントリが削除されます。

文字列セット属性に対する**和集合**ルールの例：

```json
Visitor-A: {
  "Days of week viewed confirmation": ["Monday", "Wednesday"]
}
Visitor-B: {
  "Days of week viewed confirmation": ["Wednesday", "Friday"]
}
Merged: {
  "Days of week viewed confirmation": ["Monday", "Wednesday", "Friday"]
}
```

**例：配列**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-union-array-example.png)

この例では、文字列の配列属性によって、訪問が注文確認ページを表示するたびに、その曜日が記録されます。文字列セット属性とは異なり、2 つの配列をマージした値には重複する値が含まれる場合があります。

文字列の配列属性に対する**和集合**ルールの例：

```json
Visitor-Older: {
  "Days of week viewed confirmation": ["Monday", "Wednesday", "Monday"]
}
Visitor-Active: {
  "Days of week viewed confirmation": ["Wednesday", "Friday"]
}
Merged: {
  "Days of week viewed confirmation": ["Monday", "Wednesday", "Monday", "Wednesday", "Friday"]
}
```

マージ後の属性では、元の訪問プロファイルにおける配列の順序が維持され、古い訪問のエントリが先に、アクティブな訪問のエントリが後に配置されます。
### Union Max/Min/Sum

**Union Max/Min/Sum** ルールは、共通するキーの値を特定のルール（**Max**、**Min**、または **Sum**）に基づいて組み合わせ、Tally 属性をマージします。マージ後の Tally には、元のいずれかの属性に存在するすべてのキーが保持されます。

| ルール | サポートされるデータ型 | 説明 |
|------|-------------|--------------------|
| **Union Max** |  Tally | キーをマージし、一致するキーについて大きい方の値を保持します。 |
| **Union Min** |  Tally | キーをマージし、一致するキーについて小さい方の値を保持します。 |
| **Union Sum** |  Tally | キーをマージし、一致するキーの値を加算します。 |

**例：Union Sum**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-union-sum-example.png)

この例では、Tally は訪問が商品詳細ページで閲覧した商品カテゴリーごとの回数をカウントします。**Union Sum** ルールを使用してキーをマージし、一致するキーの値を加算します。

```json
Visitor-A: {
  "Lifetime count of product categories": {
      "Accessories": 1,
      "Apparel": 2,
      "Books": 1
  }
}
Visitor-B: {
  "Lifetime count of product categories": {
      "Apparel": 4,
      "Books": 3,
      "Electronics": 5    
  }
}
Merged: {
  "Lifetime count of product categories": {
      "Accessories": 1,
      "Apparel": 6,
      "Books": 4,
      "Electronics": 5    
  }
}
```

**例：Union Max**

![](https://docs.tealium.com/images/server-side/merge-rules/rule-union-max-example.png)

この例では、Tally は商品カテゴリーが最後に閲覧された日時（エポックからの経過ミリ秒）を保存します。**Union Max** ルールを使用してキーをマージし、一致するキーについて最新の値を保持します。

```json
Visitor-A: {
  "Dates of last seen product categories": {
    "Accessories": 1702454863722,
    "Apparel": 1733414869787,
    "Books": 1731414884828
  }
}
Visitor-B: {
  "Dates of last seen product categories": {
    "Apparel": 1732424969356,
    "Books": 1733414883367,
    "Electronics": 1721357252812
  }
}
Merged: {
  "Dates of last seen product categories": {
    "Accessories": 1702454863722,
    "Apparel": 1733414869787,
    "Books": 1733414883367,
    "Electronics": 1721357252812
  }
}
```
