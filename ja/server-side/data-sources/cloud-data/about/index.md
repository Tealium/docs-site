## 要件

この機能を使用するには、次のいずれかが必要です。

* Event Streaming、Customer Data Platform（CDP）、またはData Cloud Activation

## サポートされているベンダー

クラウドデータソースの構成は、どのベンダーでもほぼ同じです。概要については、[manage-cloud-data-source](https://docs.tealium.com/manage-cloud-data-source/)を参照してください。

ベンダー固有の構成については、次を参照してください。

* [Amazon Redshift](https://docs.tealium.com/amazon-redshift-cloud-data-source/)
* [Databricks](https://docs.tealium.com/databricks-cloud-data-source/)
* [Google BigQuery](https://docs.tealium.com/google-bigquery-cloud-data-source/)
* [Snowflake](https://docs.tealium.com/about-snowflake-cloud-data-source/)

## 仕組み

クラウドデータソースは、クラウドデータウェアハウスまたはデータベースをTealiumに接続し、処理対象のイベントとしてデータをインポートできるようにします。このプロセスには、次の主要なコンポーネントがあります。

* **接続**：  
  必要な認証情報と認証の詳細を指定して、クラウドデータソースへの安全で再利用可能な接続を構成します。
* **処理**：  
  データ処理の頻度とバッチサイズを構成します。
* **クエリ構成**： 
  基本または詳細クエリ構成を選択します。基本構成では、デフォルトスキーマからインポートする列を選択し、SQLの`WHERE`句を使用してデータを絞り込めます。詳細構成では、複数のテーブルを結合し、高度なSQLコマンドを使用してデータ処理を完全に制御できます。どちらの構成でも、クエリモードを使用して、タイムスタンプ列、増分列、またはその両方により、新規または更新された行を検出する方法を制御します。
* **列のマッピング**：  
  クラウドデータベースの列をTealiumのイベント属性にマッピングします。これにより、ソースのデータがTealium内の適切な属性に正しく割り当てられます。
* **訪問IDのマッピング**：  
  複数のソースにわたってデータを統合するには、データソースの列をCustomer Data Platform（CDP）の訪問ID属性にマッピングします。これにより、訪問を正確に関連付け、プロファイルをエンリッチメントできます。

インポートされた各行はTealium内でイベントとして処理されます。これにより、クラウドシステムから一括データを取り込み、他のイベントデータと併用して、リアルタイム処理、セグメンテーション、およびアクティベーションを行えます。


<blockquote>
プロファイルごとに、同時に有効化できるクラウドデータウェアハウスのデータソースは最大10個です。
</blockquote>


## イベント処理

インポートされた各行は、列がイベント属性にマッピングされたイベントとして処理されます。イベント属性にマッピングされていない列は無視されます。

Tealiumのデフォルトの[データ収集処理順序](https://docs.tealium.com/server-side-order-of-operations/)では、クラウドデータソースからのイベントは**イベント受信**ステップの前に処理され、処理順序は変更されません。

クラウドデータソースの行は、他のデータソースからのイベントと同じ方法でEvent StreamingおよびCDPによって処理されますが、次の重要な例外があります。

* **ブラウザ固有の属性**：`User agent`などのブラウザ固有の属性は構成されません。
* **エンリッチメント**：CDPがエンリッチする事前読み込み済み属性は`First visit`のみです。事前読み込み済み属性に対するその他すべてのエンリッチメントはスキップされます。
* **単一ページ訪問**：受信イベントは、単一ページ訪問の条件から除外されます。他のデータソースからの単一ページ訪問および訪問は、CDPに保持されません。詳細については、[CDPでは単一ページ訪問はどのように処理されますか？](https://docs.tealium.com/single-event-visitor/)を参照してください。
* **訪問時間**：クラウドデータソースのイベントによって開始された訪問は60秒間継続します。
* **訪問IDのマッピング**：クラウドデータソースの構成でCDP訪問ID属性をマッピングすると、エンリッチメントを行わずに、訪問IDが選択した列の値に直接構成されます。

### スケジュール

**処理構成**セクションでは、クラウドデータソースが新しいデータをインポートする方法とタイミングを制御します。処理を有効または無効にし、データをインポートする頻度を構成できます。各インポートでは、1,000行単位のバッチでデータが処理されます。

### 頻度

データをインポートする頻度を選択します。

| **オプション** | **説明** |
| ------------------ | -------------------------------------------------------------- |
| **ほぼリアルタイム** | 2秒ごとにデータを取得します。低レイテンシーが求められるユースケースに最適です。 |
| **毎時** | 毎時0分に実行します。 |
| **毎日** | 構成した時刻（UTC）に1日1回実行します。 |
| **毎週** | 構成した曜日と時刻（UTC）に週1回実行します。 |


<blockquote>
高頻度（ほぼリアルタイムまたは毎時）でデータを取得すると、データウェアハウスのコストとシステム負荷が増加する可能性があります。
</blockquote>


### バッチサイズ

クラウドデータソースはデータをバッチ単位でインポートし、デフォルトでは1バッチあたり1,000行です。この制限は各バッチのサイズに適用され、1回のインポートで処理される行の総数には適用されません。必要なバッチ数にかかわらず、スケジュールされた各インポートは、利用可能なすべての行が取り込まれるまで処理を続行します。

次のいずれかのバッチオプションを選択します。

* **デフォルト**：1バッチあたり1,000レコード。
* **カスタム**：1,000レコードを超えるカスタムバッチを作成します。
* **制限なし**：利用可能なすべてのデータを処理する、サイズ制限のないバッチを作成します。

ユースケースに合わせてクエリのバッチサイズを最適化すると、次の利点が得られます。

* **コンピューティングコストの削減**：外部データウェアハウスおよびデータベース内のコンピューティング費用を削減します。
* **データ整合性の向上**：同一のタイムスタンプによって発生する可能性がある、重複レコードの取得を防ぎます。

クラウドプロバイダーによっては、クエリ数またはクエリサイズに基づいて料金が計算される場合があります。

[クエリモード](#query-mode-batch-processing-behavior)を選択する際には、この動作を考慮することが重要です。

### レート制限

クラウドデータソースからのインポートは通常、アカウントごとに1秒あたり200イベントに制限されますが、異なる場合があります。標準の属性サイズ制限も引き続き適用されます。詳細については、[属性について > サイズ制限](https://docs.tealium.com/about-attributes/#size-limits)を参照してください。

## クエリ構成

Tealiumのデータソースでは、データを処理するために基本と詳細の2つの構成がサポートされています。

* 基本モード：データソース構成で指定したデフォルトスキーマを使用してデータがインポートされます。処理できるデータは、1つのテーブルまたはビューのみです。必要に応じてSQLの`WHERE`句を追加し、カスタム条件に一致するレコードのみをインポートできます。
* 詳細モード：高度なSQLエディターを使用して、結合する1つ以上のテーブルを選択できます。テーブルは複数のスキーマに属していても構いません。SQLエディターでは、`CAST`や`JOIN`などの高度なSQLコマンドがサポートされています。

### データ型

クラウドデータソースは、すべてのデータ型をサポートしています。通常、データが正しくインポートされるように、次のデータ型マッピングを使用してください。

| クラウドデータ | Tealium |
|:--------------|:--------|
| 数値 | 数値属性 |
| 文字列 | 文字列属性 |
| 論理値 | ブール属性 |
| 日付と時刻 | 日付属性 |
| 配列 | 文字列の配列、数値の配列、またはブール値の配列 |
| その他 | 文字列属性 |

ベンダー固有のデータ型については、次を参照してください。

* [Amazon Redshift](https://docs.tealium.com/amazon-redshift-cloud-data-source/#data-types)
* [Databricks](https://docs.tealium.com/databricks-cloud-data-source/#data-types)
* [Google BigQuery](https://docs.tealium.com/google-bigquery-cloud-data-source/#data-types)
* [Snowflake](https://docs.tealium.com/snowflake-cloud-data-source/#data-types)

### クエリモード

クラウドデータソースでは、テーブルまたはビューからデータをインポートする方法を制御するために、次の3つのクエリモードがサポートされています。

* タイムスタンプ + 増分
* タイムスタンプ
* 増分

各モードでは、タイムスタンプ列、増分列、またはその両方を使用して、インポートする行を決定します。
#### 列の要件

クエリモードを効果的に機能させるには、次の一方または両方が必要です。

* **タイムスタンプ列**  
行が追加または変更されたときに現在時刻が構成されるタイムスタンプ列。タイムスタンプ列が適切に構成されていない場合、行が読み取られなかったり、複数回読み取られたりする可能性があります。
* **増分列**  
行が追加されるたびに値が増加する数値列。自動増分列には、次の定義を推奨します。
  ```sql
  COL1 NUMBER AUTOINCREMENT START 1 INCREMENT 1
  ```
  この定義により、新しい行が追加されるたびに常に昇順となる一意のキーが生成されます。常に昇順となる一意のキーがない場合、行が読み取られなかったり、複数回読み取られたりする可能性があります。

ベンダー固有の要件については、以下を参照してください。

* [Amazon Redshift](https://docs.tealium.com/amazon-redshift-cloud-data-source/#query-configurations)
* [Databricks](https://docs.tealium.com/databricks-cloud-data-source/#query-configurations)
* [Google BigQuery](https://docs.tealium.com/google-bigquery-cloud-data-source/#query-configurations)
* [Snowflake](https://docs.tealium.com/snowflake-cloud-data-source/#query-configurations)

ユースケースの要件に合ったモードを選択してください。これらのモードの動作例については、[クエリモードのバッチ処理動作](#query-mode-batch-processing-behavior)を参照してください。

#### タイムスタンプ＋増分（推奨）

このモードでは、タイムスタンプ列と増分列の両方を使用して、新規または変更された行をインポートします。

前回のインポートより新しいタイムスタンプを持つ行、またはタイムスタンプが同じで増分値が大きい行がインポートされます。

このモードは、すべての行が意図どおりにインポートされることを保証するうえで最も高い信頼性を提供します。

#### タイムスタンプ

このモードでは、タイムスタンプ列を使用して新規または更新された行をインポートします。

前回のインポートより新しいタイムスタンプを持つ行のみがインポートされます。同じタイムスタンプを持つ行をインポートしようとすると、タイムスタンプが重複している行がインポートされない場合があります。

テーブルに、挿入または更新操作のたびに値が構成されるタイムスタンプ列がある場合は、このモードを使用します。

#### 増分

このモードでは、増分列を使用して行をインポートします。

最後にインポートされた行より大きい増分値を持つ行がインポートされます。増分値が前回のインポートの最大値以下である行はスキップされます。このモードでは、既存の行に対する変更は検出されません。

テーブルにタイムスタンプ列がない場合は、このモードを使用します。

自動増分列を使用せずに独自の増分列を管理する場合は、値が常に増加するようにしてください。

#### クエリモードのバッチ処理動作

各クエリモードでは、バッチの終了時にシステムが記録する境界値が決まります。次のバッチでは、記録されたこれらの値を使用して、取得する行を決定します。

| クエリモード | バッチ境界で記録される値 |
|---|---|
| タイムスタンプ＋増分 | 最後のタイムスタンプ値と最後の増分値 |
| タイムスタンプ | 最後のタイムスタンプ値のみ |
| 増分 | 最後の増分値のみ |

次の例は、これらのバッチ境界が、次のバッチでインポートされる行にどのように影響するかを示しています。

この例では、クラウドデータソースが、スケジュールされた実行ごとに1,000行ずつ直列バッチでデータを取得し、レコードが返されなくなるまで処理を続けます。使用するクエリモードによっては、行1001がインポートされる場合とされない場合があります。

次の表では、`modification_time`がタイムスタンプ列、`customer_id`が増分列であり、「バッチ」は行が処理されるバッチを示します。

| `customer_id` | `modification_time` | `customer_segment` | バッチ |
|---------------|---------------------|--------------------|-------|
| `1`           | `01Apr 13:00`       | `A`                | A     |
| `2`           | `01Apr 13:00`       | `B`                | A |
| ...           | ...                 | ...                | A |
| `1000`        | `01Apr 13:00`       | `D`                | A |
| `1001`        | `01Apr 13:00`       | `E`                | ? |
| `1002`        | `02Apr 14:00`       | `A`                | B |

バッチA（行1～1000）の処理後、選択したクエリモードに応じて、検出された最大値がシステムに記録されます。次のバッチでは、これらの値を使用して取得する行を決定します。

#### タイムスタンプ＋増分

タイムスタンプ＋増分モードを使用すると、次のSQLクエリによってすべての行が正常に処理されます。

**バッチA**のクエリ：

```sql
SELECT * FROM customers
WHERE modification_time < NOW()
ORDER BY modification_time, customer_id ASC
LIMIT 1000
```

バッチAの処理が完了すると、システムは次の値を記録します。

* 最終バッチのタイムスタンプ：`01Apr 13:00`
* 最終バッチのID：`1000`

**バッチB**のクエリ：

```sql
SELECT * FROM customers
WHERE modification_time < NOW()
AND ((modification_time = '01Apr 13:00' AND customer_id > 1000)
OR modification_time > '01Apr 13:00')
ORDER BY modification_time, customer_id ASC
LIMIT 1000
```

行1001は、タイムスタンプが同じでもID値が大きいため、正常にインポートされます。行1002は、より新しいタイムスタンプを持つためインポートされます。

#### 増分

増分モードを使用すると、各バッチの後に追加された行は処理されますが、既存の行に対する変更は検出されない場合があります。

**バッチA**のクエリ：

```sql
SELECT * FROM customers
ORDER BY customer_id ASC
LIMIT 1000
```

バッチAの処理が完了すると、システムは次の値を記録します。

* 最終バッチのID：`1000`

**バッチB**のクエリ：

```sql
SELECT * FROM customers
WHERE customer_id > 1000
ORDER BY customer_id ASC
LIMIT 1000
```

行1001と1002は、より大きいID値を持つためインポートされます。ただし、バッチAの後に行1～1000のいずれかが変更されても、その更新は検出されません。

#### タイムスタンプ（この例では`modification_time`）

タイムスタンプモードを使用すると、行の欠落が発生します。

**バッチA**のクエリ：

```sql
SELECT * FROM customers
WHERE modification_time < NOW()
ORDER BY modification_time ASC
LIMIT 1000
```

バッチAの処理が完了すると、システムは次の値を記録します。

* 最終バッチのタイムスタンプ：`01Apr 13:00`

**バッチB**のクエリ：

```sql
SELECT * FROM customers
WHERE modification_time > '01Apr 13:00'
ORDER BY modification_time ASC
LIMIT 1000
```

行1001のタイムスタンプ値は前回のバッチ境界と同じであるため、システムによってスキップされます。行1002のみがインポートされます。


<blockquote>
バッチ境界で数千件のレコードが同じタイムスタンプを共有している場合、バッチ全体がスキップされることがあります。多数のレコードが同時に挿入または更新されるソースデータウェアハウスへの一括インポートでは、複数のレコードが同じタイムスタンプを共有することがよくあります。
</blockquote>


## 列マッピング

列マッピング構成では、クラウドデータベーステーブルの各列に対応するイベント属性を指定します。

列名はTealiumアカウント内の属性名と異なることが多いため、このマッピングによってデータが適切にインポートされるようにします。たとえば、テーブルで列名`postalCode`を使用し、Tealiumのイベント属性が`customer_zip`である場合は、これらのフィールドを関連付けるマッピングを作成します。

クラウドデータ型からTealiumデータ型へのマッピングについては、[データ型](#data-types)セクションを参照してください。

ベンダー固有のデータ型については、以下を参照してください。

* [Amazon Redshift](https://docs.tealium.com/amazon-redshift-cloud-data-source/#data-types)
* [Databricks](https://docs.tealium.com/databricks-cloud-data-source/#data-types)
* [Google BigQuery](https://docs.tealium.com/google-bigquery-cloud-data-source/#data-types)
* [Snowflake](https://docs.tealium.com/snowflake-cloud-data-source/#data-types)

## 訪問IDのマッピング

インポートしたデータをWeb、モバイル、HTTP APIなどの他のソースと統合できるようにするため、テーブル内のすべての行に一意の訪問IDを含む列があることを確認してください。

訪問ID列と対応するイベント属性を、訪問ID属性（CDPで訪問を識別するための一意の属性タイプ）にマッピングします。マッピングされたイベント属性の値は`tealium_visitor_id`属性に割り当てられ、既存の訪問プロファイルと直接照合されます。

AudienceStreamでの訪問IDマッピングの詳細については、[Tealiumデータソースを使用した訪問識別](https://docs.tealium.com/visitor-identification-data-sources/)を参照してください。
## 許可するIPアドレス

クラウドデータアカウントでリクエストを受け付けるシステムが厳格に制限されている場合は、[TealiumのIPアドレス]()をクラウドデータベースの許可リストに追加してください。
