## 大規模な訪問プロファイルの操作

[**訪問データ全体を送信**アクション](#send-entire-visitor-data-micro-batch)では、訪問の完全なJSONが各SQL INSERTステートメントに埋め込まれます。Redshift Data APIでは、SQLステートメントごとに100 kBの制限が適用されるため、訪問プロファイルがこの制限を超えると、コネクタアクションは次のエラーで失敗します：`ValidationException: Query string size exceeds 100 kB`。

この問題を回避するには、次のガイドラインに従ってください。

* **小規模な訪問プロファイルには「訪問データ全体を送信」を使用します。**  
数キロバイトを超える訪問プロファイルでは、制限を超えるリスクが高まります。訪問プロファイルが100 kBの制限を十分に下回る場合に、このアクションを使用してください。[訪問検索](https://docs.tealium.com/visitor-search/)を使用して完全なプロファイルを取得し、そのサイズを評価します。
* **プロファイル全体ではなく、マッピングした属性を送信します。**  
訪問の完全なJSONを送信する代わりに、[**カスタム訪問データを送信**](#send-custom-visitor-data-micro-batch)アクションを使用して、必要な属性のみを選択します。
* **一括読み込みまたは履歴データの読み込みには、S3とRedshiftを使用します。**  
大規模な訪問JSONペイロードや単発の一括アップロードでは、訪問データを[S3コネクタ](https://docs.tealium.com/amazon-s3-connector/)に送信してから、COPYコマンドを使用してRedshiftにデータを読み込みます。詳細については、[Amazon Redshift：COPYコマンドを使用したAmazon S3からの読み込み](https://docs.aws.amazon.com/redshift/latest/dg/t_loading-tables-from-s3.html)を参照してください。
* **大規模なペイロードにはWebhook（JDBC）コネクタを使用します。**
[Webhook（JDBC）コネクタ](https://docs.tealium.com/webhook-jdbc/)は、JDBC経由でRedshiftに直接接続し、Redshift Data APIの100 kBの制限を回避します。訪問プロファイルが100 kBを超える場合は、このオプションを使用してください。

## 構成

コネクタマーケットプレイスに移動し、新しいコネクタを追加します。詳細については、[about-connectors](https://docs.tealium.com/about-connectors/)を参照してください。

コネクタを追加したら、次の構成を構成します。

* **認証タイプ**  
  * 認証タイプを選択します。
    * **STS**：**引き受けるロール：ARN**と**引き受けるロール：セッション名**のフィールドが必要です。詳細については、[STS認証情報](#sts-credentials)を参照してください。
    * **アクセスキー**：**AWSアクセスキー**と**AWSシークレットアクセスキー**のフィールドが必要です。詳細については、[アクセスキーとシークレットの認証情報](#access-key-and-secret-credentials)を参照してください。
* **STS - 引き受けるロール：ARN**  
  * STS認証では必須です。引き受けるロールのAmazonリソースネーム（ARN）を指定します。
  * 例：`arn:aws:iam:222222222222:role/myrole`
  * 詳細については、[AWS：IAMロールへの切り替え](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-api.html)を参照してください。
* **STS - 引き受けるロール：セッション名**  
  * STS認証では必須です。引き受けるロールのセッション名を指定します。
  * 最小文字数は2文字、最大文字数は64文字です。
* **STS - 引き受けるロール：外部ID**  
  * サードパーティの外部識別子を指定します。
  * 詳細については、[AWS：サードパーティが所有するAWSアカウントへのアクセス](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_common-scenarios_third-party.html)を参照してください。
* **アクセスキー - AWSアクセスキー**  
  * アクセスキー認証では必須です。AWSアクセスキーを指定します。
* **アクセスキー - AWSシークレットアクセスキー**  
  * アクセスキー認証では必須です。AWSシークレットアクセスキーを指定します。
* **リージョン**  
  * （必須）リージョンを選択します。
* **シークレット名**  
  * （任意）AWS Secrets Manager方式を使用してRedshiftにアクセスする場合は、Redshift接続で使用するシークレットARNをTealiumが動的に取得できるように、シークレット名を指定します。
* **ワークグループ名**  
  * **クラスター識別子**を指定しない場合は必須です。Redshift SERVERLESSインスタンスにアクセスする場合は、ワークグループ名を指定します。
* **クラスター識別子**  
  * **ワークグループ名**を指定しない場合は必須です。Redshiftクラスターを使用している場合は、クラスター識別子を指定します。
* **データベース名**  
  * （任意）データベース名を指定します。デフォルト値：`dev`

### AWS Redshiftへの接続の作成

クラスター、ワークスペース、データベースの一覧を表示し、イベントデータとオーディエンスデータをRedshiftテーブルにアップロードするには、TealiumからAWS Redshiftインスタンスへの接続が必要です。認証には次の2つのオプションがあります。

* [アクセスキーとアクセスシークレットを指定する](#access-key-and-secret-credentials)。
* [STS認証情報を指定する](#sts-credentials)。

コネクタを構成したら、**完了**をクリックします。

#### アクセスキーとシークレットの認証情報

AWSアクセスキーとシークレットを確認するには、次の手順を実行します。

1. AWS Management Consoleにログインし、**IAM**（Identity and Access Management）サービスに移動します。
1. **ユーザー**をクリックし、**ユーザーを追加**をクリックします。
1. ユーザー名を入力します。例：`TealiumRedshiftUser`
1. ロールにポリシーをアタッチします。詳細については、[ポリシーのアタッチ](#attach-policies)を参照してください。
1. キーを作成します。
    * **セキュリティ認証情報**タブに移動し、**アクセスキーを作成**をクリックします。
    * **アクセスキーID**と**シークレットアクセスキー**をコピーし、安全に保存します。

#### STS認証情報

STS認証情報を確認するには、次の手順を実行します。

1. AWS Management Consoleにログインし、**IAM**（Identity and Access Management）サービスに移動します。
1. **ロール**をクリックし、**ロールを作成**をクリックします。
1. **信頼されたエンティティタイプ**で、AWSアカウントを選択します。
1. 「別のAWSアカウント」を選択し、TealiumアカウントID `757913464184`を入力します。
1. （任意）**外部IDを要求する**チェックボックスをオンにし、使用する外部IDを指定します。外部IDは最大256文字で、英数字（`A-Z`、`a-z`、`0-9`）およびハイフン（`-`）、アンダースコア（`_`）、ピリオド（`.`）などの記号を使用できます。
1. ロール名を入力します。ロール名は`TealiumRedshift`で始まる必要があります。例：`TealiumRedshift-test`
1. ロールにポリシーをアタッチします。詳細については、[ポリシーのアタッチ](#attach-policies)を参照してください。
1. 信頼ポリシーを作成します。
    * **信頼関係**タブに移動し、**信頼関係を編集**をクリックします。
    * 作成したロールを指定の外部IDが使用できること、およびTealiumの本番アカウントIDが`757913464184`であることを信頼ポリシーで許可していることを確認します。
    * Tealiumへの接続用に`EXTERNAL_ID`の値を構成します。このIDは最大256文字で、英数字（`A-Z`、`a-z`、`0-9`）およびハイフン（`-`）、アンダースコア（`_`）、ピリオド（`.`）などの記号を使用できます。
    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": {
            "AWS": "arn:aws:iam::757913464184:root"
          },
          "Action": "sts:AssumeRole",
          "Condition": {
            "StringEquals": {
              "sts:ExternalId": "EXTERNAL_ID"
            }
          }
        }
      ]
    }
    ```
#### ポリシーのアタッチ

ポリシーをアタッチするには、次の手順を実行します。

1. **Permissions**タブで、**Attach existing policies directly**をクリックします。
    1. フルアクセス
        * フルアクセスを付与するには、`SecretsManagerReadWrite`、`AmazonRedshiftAllCommandsFullAccess`、`AmazonRedshiftDataFullAccess`ポリシーを検索してアタッチします。
    1. 制限付きアクセス
        * 特定のクラスターへのアクセスを制限するには、次の例のようなポリシーを作成します。この例で、`YOUR_CLUSTER_ARN`は、Tealiumがイベントデータとオーディエンスデータを`YOUR_DATABASE_ARN`のRedshiftテーブルに挿入する際に使用するクラスターです。
        ```json
        {
          "Version": "2012-10-17",
          "Statement": [
            {
              "Sid": "RedshiftClusterManagement",
              "Effect": "Allow",
              "Action": [
                "redshift:DescribeClusters",
                "redshift:GetClusterCredentials",
                "redshift:GetClusterCredentialsWithIAM"
              ],
              "Resource": "arn:aws:redshift:YOUR_REGION:YOUR_ACCOUNT_ID:cluster/YOUR_CLUSTER_ARN"
            },
            {
              "Sid": "RedshiftDataAPI",
              "Effect": "Allow",
              "Action": [
                "redshift-data:ExecuteStatement",
                "redshift-data:BatchExecuteStatement",
                "redshift-data:DescribeStatement",
                "redshift-data:GetStatementResult",
                "redshift-data:ListStatements"
              ],
              "Resource": "arn:aws:redshift:YOUR_REGION:YOUR_ACCOUNT_ID:database/YOUR_DATABASE_ARN"
            },
            {
              "Sid": "SecretsManagerAccess",
              "Effect": "Allow",
              "Action": [
                "secretsmanager:GetSecretValue",
                "secretsmanager:DescribeSecret",
                "secretsmanager:ListSecrets"
              ],
              "Resource": "arn:aws:secretsmanager:YOUR_REGION:YOUR_ACCOUNT_ID:secret/YOUR_SECRET_ARN"
            }
          ]
        }
        ```

        * 特定のワークグループへのアクセスを制限するには、次の例のようなポリシーを作成します。この例で、`YOUR_WORKGROUP_ARN`は、Tealiumがイベントデータとオーディエンスデータを`YOUR_DATABASE_ARN`のRedshiftテーブルに挿入する際に使用するクラスターです。

        ```json
        {
          "Version": "2012-10-17",
          "Statement": [
            {
              "Sid": "RedshiftServerlessAccess",
              "Effect": "Allow",
              "Action": [
                "redshift-serverless:GetWorkgroup",
                "redshift-serverless:GetCredentials",
                "redshift-serverless:ListWorkgroups"
              ],
              "Resource": "arn:aws:redshift-serverless:YOUR_REGION:YOUR_ACCOUNT_ID:workgroup/YOUR_WORKGROUP_ARN"
            },
            {
              "Sid": "RedshiftDataAPI",
              "Effect": "Allow",
              "Action": [
                "redshift-data:ExecuteStatement",
                "redshift-data:BatchExecuteStatement",
                "redshift-data:DescribeStatement",
                "redshift-data:GetStatementResult",
                "redshift-data:ListStatements"
              ],
              "Resource": "arn:aws:redshift:YOUR_REGION:YOUR_ACCOUNT_ID:database/YOUR_DATABASE_ARN"
            },
            {
              "Sid": "SecretsManagerAccess",
              "Effect": "Allow",
              "Action": [
                "secretsmanager:GetSecretValue",
                "secretsmanager:DescribeSecret",
                "secretsmanager:ListSecrets"
              ],
              "Resource": "arn:aws:secretsmanager:YOUR_REGION:YOUR_ACCOUNT_ID:secret/YOUR_SECRET_ARN"
            }
          ]
        }
        ```

| イベントデータ全体を送信（バッチ） | ✗ | ✓ |
| カスタムイベントデータを送信（マイクロバッチ） | ✗ | ✓ |

アクション名を入力し、ドロップダウンメニューからアクションタイプを選択します。

以降のセクションでは、各アクションのパラメータとオプションを構成する方法について説明します。

### イベントデータ全体を送信（マイクロバッチ）

#### バッチ制限

このアクションでは、ベンダーへの大量のデータ転送に対応するため、バッチリクエストを使用します。詳細については、[バッチアクション](https://docs.tealium.com/batched-actions/)を参照してください。次のいずれかのしきい値に達するか、プロファイルがパブリッシュされるまで、リクエストはキューに格納されます。

* リクエストの最大数：50
* 最も古いリクエストからの最大経過時間：16分

#### パラメータ

| パラメータ | 説明 |
| --- | --- |
| スキーマ | 接続先のスキーマ名を指定します。 |
| テーブル | 接続先のテーブル名を指定します。 |
| ペイロードを記録する列 | ペイロードを記録する`SUPER`列を選択します。 |
| タイムスタンプを記録する列 | タイムスタンプを記録する列を選択します。テーブルに**デフォルトのsysdate**が構成された**timestamp**列がすでにある場合、この構成は不要です。 |
| 属性名を出力 | デフォルトでは、属性キーが使用されます。代わりに属性名をキーとして使用する場合は、このチェックボックスを有効にします。属性名が更新されると、ペイロード内の名前にも更新が反映されることに注意してください。 |
| バッチの有効期間 | バッチアクションを送信する頻度を指定するため、有効期間（TTL）を構成します。`1`～`16`分の値を入力します。デフォルト値は`5`分です。 |

* 最も古いリクエストからの最大経過時間：60分

| パラメータ | 説明 |
| --- | --- |

| すべての訪問イベントを含める | 訪問データに現在の訪問データを含めます。 |
| 属性名を出力 | デフォルトでは属性キーが使用されます。代わりに属性名をキーとして使用する場合は、このチェックボックスを有効にします。属性名が更新されると、ペイロード内の名前にもその更新が反映されることに注意してください。 |
| バッチの有効期間 | バッチアクションを送信する頻度を指定するため、有効期間（TTL）を構成します。`15`～`60`分の値を入力します。デフォルト値は`30`分です。 |

### カスタムステートメントを実行（バッチ）

#### バッチ制限

このアクションでは、ベンダーへの大量データ転送をサポートするためにバッチリクエストを使用します。詳細については、[バッチアクション](https://docs.tealium.com/batched-actions/)を参照してください。次のいずれかのしきい値に達するか、プロファイルがパブリッシュされるまで、リクエストはキューに保持されます。

* リクエストの最大数：40
* 最も古いリクエストからの最大経過時間：60分

#### パラメータ

| パラメータ | 説明 |
| --- | --- |
| スキーマ | 接続先のスキーマ名を指定します。 |
| テーブル | 接続先のテーブル名を指定します。 |
| クエリパラメータ | クエリ内で置換するプレースホルダーにパラメータをマッピングします。少なくとも1つのパラメータをマッピングする必要があります。 |
| クエリ | `SQL`属性に渡す未加工のステートメントを指定します。使用できるのは`INSERT`、`UPDATE`、または`MERGE`ステートメントのみです。変数を参照するには、属性名の前に`:`を追加します。詳細については、[クエリの例](#query-example)を参照してください。|
| バッチの有効期間 | バッチを送信するまでの待機時間です。`1`～`60`分の値を指定できます。デフォルト値は`15`分です。 |

#### クエリの例

**クエリパラメータ**セクションに`my_boolean_tealium_attribute = MY_BOOLEAN_PARAM`のようなマッピングを追加した場合、クエリでは`:MY_BOOLEAN_PARAM`を使用してそのパラメータを参照します。

次のクエリパラメータをマッピングした場合のクエリ例：`MY_STRING_PARAM`、`MY_BOOLEAN_PARAM`、`ANOTHER_PARAM`、`MY_PARAM`。

```sql
INSERT INTO redshift_table
  (key1, key2) VALUES (':MY_STRING_PARAM', :MY_BOOLEAN_PARAM);
UPDATE redshift_table SET
  key1 = ':MY_STRING_PARAM',
  key2 = :MY_BOOLEAN_PARAM
WHERE
  key3 = ':ANOTHER_PARAM';
UPDATE redshift_table
  SET key2 = (SELECT new_key2 FROM source_table WHERE source_table.key1 = redshift_table.key1)
WHERE EXISTS
  (SELECT 1 FROM source_table WHERE source_table.key1 LIKE %:MY_PARAM%);
```

#### デバッグ

Tealiumから成功レスポンスが返されてもデータがRedshiftに表示されない場合、SQLステートメントはTealiumによって受け付けられた後、Redshiftによって拒否された可能性があります。

調査するには、次の手順を実行します。

1. [トレース](https://docs.tealium.com/about-trace/)を実行し、成功した呼び出しのレスポンス本文に含まれるIDを記録します。
1. [Amazon Redshift Data API](https://docs.aws.amazon.com/redshift-data/latest/APIReference/API_DescribeStatement.html)を使用して、SQLステートメントの詳細を確認します。

次のリクエストを送信し、`Id`の値をトレースで取得したIDに置き換えます。

```http
POST / HTTP/1.1
Host: redshift-data.us-east-1.amazonaws.com
X-Amz-Target: RedshiftData.DescribeStatement
Content-Type: application/x-amz-json-1.1
Authorization: AUTHORIZATION_HEADER
X-Amz-Date: TIMESTAMP

{
    "Id": "37eb2735-b467-4852-884b-0f536970bf7e"
}
```

レスポンスには、ステートメントのステータスと、Redshiftから返されたエラーメッセージが含まれます。
