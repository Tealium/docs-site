## 構成

コネクタマーケットプレイスに移動し、新しいコネクタを追加します。詳細については、[about-connectors](https://docs.tealium.com/about-connectors/)を参照してください。

コネクタを追加した後、以下の構成を構成します。

* **認証タイプ**
  * **SASL/PLAIN**（デフォルト）：ユーザー名とパスワードを使用して認証します。
  * **SASL SCRAM-SHA-512**：SCRAM-SHA-512チャレンジレスポンス認証を使用します。このオプションを選択する前に、Kafkaブローカーが`SCRAM-SHA-512`メカニズムをサポートするように構成してください。
* **ブートストラップサーバー**
  * （必須）エンドポイントのKafkaブートストラップサーバー（Conduktor GatewayホストやKafkaブローカーなど）：`gateway.customer-domain.com:6969`。
  * エンドポイントは、通常PrivateLink、VPN、またはネットワークピアリングを介してTealiumから到達可能である必要があります。
* **CA証明書（PEM）**
  * Kafkaブローカーまたはゲートウェイから提示されるTLS証明書の検証に使用する、PEMエンコードされたCA証明書チェーン。
  * エンドポイントで内部PKI、プライベートCA、または自己署名証明書を使用する場合は必須です。
* **ホスト名検証を無効化**
  * ホスト名がTLS証明書と一致することの検証を無効にします。
  * SNIまたは標準以外のホスト名を使用する場合は、この構成を無効にします。デフォルト：検証は有効。
* **Confluent Schema Registry URL**
  * （任意）Schema RegistryのURL（例：`https://schema-registry.example.com:8081`）。
  * カスタムアクションでスキーマ検証を使用する場合は必須です。
* **Confluent Schema Registryユーザー名**
  * （任意）HTTP Basic認証を使用してSchema Registryに認証するためのユーザー名。
  * Schema Registryで認証が必要な場合は必須です。
* **Confluent Schema Registryパスワード**
  * （任意）HTTP Basic認証を使用してSchema Registryに認証するためのパスワードまたはAPIシークレット。
  * Schema Registryで認証が必要な場合は必須です。
* **サービスアカウントのユーザー名**
  * （必須）ブローカーへの認証に使用するKafkaプリンシパル。
  * SASL/PLAINの場合は、SASLユーザー名を入力します。SASL SCRAM-SHA-512の場合は、SCRAMプリンシパルを入力します。
* **サービスアカウントのトークン／パスワード**
  * （必須）サービスアカウントプリンシパルの認証情報。
  * SASL/PLAINの場合は、JWTトークンまたは同等の認証情報を入力します。SASL SCRAM-SHA-512の場合は、SCRAMパスワードを入力します。
* **圧縮タイプ**
  * Kafkaに送信するメッセージに使用する圧縮アルゴリズム。帯域幅と保存のコストを削減します。
  * デフォルトは`GZIP`です。
* **最大メッセージサイズ（バイト）**
  * 1回のリクエストで送信される単一メッセージまたはバッチの最大サイズ（バイト単位）。大きな訪問プロファイルに対応するにはこの値を増やしますが、ブローカーの構成と一致していることを確認してください。
  * デフォルトは`1,048,576`バイト（1 MB）です。最大値は`2,097,152`バイト（2 MB）です。
  * この値は、Kafkaブローカーの`message.max.bytes`構成を超えてはなりません。
* **クライアントID**
  * ロギング、監視時の帰属判定、クォータ適用のために、各リクエストとともにブローカーへ送信される識別子。
  * デフォルトでは、次の形式で自動生成された識別子が使用されます：`tealium-{account}-{profile}-{connectorId}`。
  * 使用できる文字は、英字、数字、ピリオド（`.`）、ハイフン（`-`）、およびアンダースコア（`_`）です。
* **確認応答（acks）**
  * メッセージが正常に書き込まれたと見なされるまでに必要なブローカーの確認応答数を指定します。
  * **0**：確認応答なし。最も高速ですが、通知されないままデータが失われるリスクがあります。
  * **1**：パーティションリーダーがメッセージをローカルに書き込んだ後に確認応答します。配信保証を備えた最速のオプションです。
  * **すべて**：同期中のすべてのレプリカが確認応答する必要があります。レイテンシーが50～100ミリ秒増加しますが、データ損失のリスクがなくなります。
* **パーティショナー戦略**
  * パーティションが指定されていない場合に、プロデューサーがメッセージをパーティションへ割り当てる方法を制御します。
  * **デフォルト**：最適なスループットを実現するため、スティッキーバッチ処理を使用します。
  * **ラウンドロビン**：すべてのパーティションにメッセージを均等に分散します。
  * メッセージキーが構成されている場合、この構成にかかわらず、メッセージは常にキーのハッシュに基づいてパーティショニングされます。
* **プロデューサー - 再接続バックオフ**
  * 接続に失敗した後、ブローカーへ再接続するまでの待機時間（ミリ秒）。
  * デフォルトは`50`ミリ秒です。
* **プロデューサー - 再試行回数**
  * 送信操作に失敗した場合の最大再試行回数。
  * 空白のままにすると、Kafkaクライアントのデフォルト値が使用されます。
* **プロデューサー - 再試行バックオフ**
  * 同じレコードの再試行間の待機時間（ミリ秒）。
  * デフォルトは`100`ミリ秒です。

コネクタを構成した後、**完了**をクリックします。

## アクション

| アクション名 | 訪問プロファイル | イベントデータ |
| ----------- | :------------: | :---------: |
| すべてのイベントデータを送信 | ✗ | ✓ |
| すべての訪問データを送信 | ✓ | ✗ |
| カスタムイベントデータを送信 | ✗ | ✓ |
| カスタム訪問データを送信 | ✓ | ✗ |
| すべてのログイベントを送信 | ✗ | ✓ |
| ログイベントを送信 | ✗ | ✓ |

**続行**をクリックして、コネクタアクションを構成します。アクションの名前を入力し、リストからアクションタイプを選択します。

以下のセクションでは、各アクションのパラメータとオプションを構成する方法について説明します。

### すべてのイベントデータを送信

#### パラメータ

| パラメータ | 説明 |
| --- | --- |
| トピック | トピックを選択するか、トピックIDを入力します。 |
| データ形式 | データ配信の形式として、`JSON`、`STRING`、または`BINARY`を指定します。 |
| パーティションID | （任意）パーティションIDを選択します。空白のままにすると、メッセージキーまたはラウンドロビンに基づいてKafkaのデフォルトパーティショナーが使用されます。 |
| ヘッダー | （任意）Kafkaレコードのヘッダーに追加するキーと値のペアのセット。 |
| メッセージキー | （任意）未加工のメッセージキーを指定します。データ形式が`BINARY`に構成されている場合、この値は送信前にエンコードされます。 |
| タイムスタンプ | （任意）ISO 8601 UTC形式`YYYY-MM-DDThh:mm:ssZ`のメッセージタイムスタンプ。指定しない場合は、現在のタイムスタンプが使用されます。 |
| 属性名を出力 | デフォルトでは、属性キーが使用されます。代わりに属性名をキーとして使用するには、このオプションを有効にします。 |
| バッチの有効期間 | バッチの有効期間（分単位、1～60）。デフォルト：10。 |

#### パラメータ

| パラメータ | 説明 |
| --- | --- |
| トピック | トピックを選択するか、トピックIDを入力します。 |
| データ形式 | データ配信の形式として、`JSON`、`STRING`、または`BINARY`を指定します。 |
| パーティションID | （任意）パーティションIDを選択します。空白のままにすると、メッセージキーまたはラウンドロビンに基づいてKafkaのデフォルトパーティショナーが使用されます。 |
| ヘッダー | （任意）Kafkaレコードのヘッダーに追加するキーと値のペアのセット。 |
| メッセージキー | （任意）未加工のメッセージキーを指定します。データ形式として**BINARY**を選択した場合、Tealiumはこの値をエンコードしてから送信します。 |
| タイムスタンプ | （任意）ISO 8601 UTC形式`YYYY-MM-DDThh:mm:ssZ`のメッセージタイムスタンプ。指定しない場合は、現在のタイムスタンプが使用されます。 |

| 現在の訪問データを訪問データに含める | 現在の訪問データを訪問データのペイロードに含めます。 |
| バッチの有効期間 | バッチの有効期間（分単位、1～60）。デフォルト：10。 |

### カスタムイベントデータを送信
#### パラメータ

| パラメータ | 説明 |
| --- | --- |
| トピック | トピックを選択するか、トピック ID を入力します。 |
| データ形式 | データ配信の形式として、`JSON`、`STRING`、または `BINARY` を指定します。 |
| スキーマ | （任意）Schema Registry からスキーマサブジェクトを選択します。Schema Registry URL が構成されている必要があります。 |

| ヘッダー | （任意）Kafka レコードのヘッダーに追加するキーと値のペアのセットです。 |
| メッセージキー | （任意）未加工のメッセージキーを指定します。データ形式として **BINARY** を選択した場合、Tealium は送信前にこの値をエンコードします。 |
| タイムスタンプ | （任意）メッセージのタイムスタンプを ISO 8601 UTC 形式（`YYYY-MM-DDThh:mm:ssZ`）で指定します。指定しない場合は、現在のタイムスタンプが使用されます。 |
| バッチの有効期間 | バッチの有効期間（分単位、1～60）です。デフォルト：10。 |
